Hook time budget (branch fix/hook-time-budget, 2026-11-05; docs/how-it-works.md "Hooks", docs/troubleshooting.md). Cause of `UserPromptSubmit hook timed out after 5s — output discarded`: every SQLite statement waited up to 2 s (`timeout: 2000` in SqliteAdapter) for another process's write lock, a handler runs several statements, and nothing capped the total. A swarm run puts many processes on one project database (workers' hooks, indexer, usage ingest). Reproduced on a copy of the real project database: 6 processes holding write transactions (300 ms, back to back) gave hooks of 5.0 to 6.7 s; the same load after the fix gives 1.1 to 1.3 s. With no contention a hook takes 70 to 130 ms, and 30 concurrent hooks on a free database finish in under 1 s, so the cost was lock waits, not the work.

- Hooks open the database with a lock wait from `lockWaitFor(raw, argv)` → `busyTimeoutFor(event, tool)` (src/hooks/budget.ts, set in src/hook.ts through `setStorageBusyTimeout` before `dispatch`); the CLI and servers keep 2000. `lockWaitFor` uses `handlerEvent` (src/hooks/cursor.ts): `--event` forced as dispatch does, and a Cursor payload's camelCase event and tool names translated first, so Cursor's `sessionStart`/`subagentStop`/`stop`/`sessionEnd`/`afterFileEdit` get the write waits (reading the raw name gave every Cursor hook 250). tests/unit/hook-budget.test.ts runs src/hook.ts itself (node --import tsx) under a held lock, so a mutant in the wiring fails. Read-only and prompt hooks (UserPromptSubmit, other PreToolUse, PostToolUseFailure of other tools) get `HOOK_BUSY_TIMEOUT_MS` = 250. Write-job hooks wait longer because losing the write leaves a worker holding its slot: SessionStart, PostToolUse, SubagentStart, PreCompact 2000 ms; SubagentStop, SessionEnd, Stop 1500 ms; PreToolUse Agent/Task (spawn reservation) 1500 ms; PostToolUseFailure Agent/Task 1500 ms, because it releases that reservation (`swarmAgentReturned`) and a lost release keeps the slot until SPAWN_TTL_MS (2 min), so the retry is denied. That release runs first; the writes after it (swarm activity, session row, recordShown, the failure event; `bestEffortWrites` in src/hooks/capture.ts) wait HOOK_BUSY_TIMEOUT_MS each through `db.adjudicator.withLockWait`, are not started with under 1000 ms of budget left, and the first locked one skips the rest (task #276: an 8 s lock took the built hook 5047 ms, now ~2.05 s with the recall still returned).
- Best effort vs required: UserPromptSubmit, SessionStart and PostToolUseFailure still answer when the database is locked (session row and event writes are skipped, reads still run). The write-job hooks are not best effort; past their wait they fail open with `{}`, except SubagentStart, which tries registerWorker three times (400 ms pauses; ~7.4 s under a held lock) and then answers `fallbackBrief` (worker unregistered, told how to claim). So a busy database costs only bookkeeping for the best-effort hooks, not for every hook.
- A PreToolUse Agent/Task call denied at the deadline or by a handler error (`failClosed` in src/hooks/dispatch.ts) releases the spawn reservation it made, so the retry is not refused.
- `dispatch()` runs the handler against `budgetFor(event)`: 3.5 s for the 5 s hooks, 8 s SessionStart/PostToolUse/SubagentStart, 12 s PreCompact. On the deadline it answers `{}` (a denied swarm dispatch stays denied via `failClosed`), sets `ranLate()`, and src/hook.ts exits after writing the answer. A synchronous SQLite wait cannot be interrupted, so the deadline only bounds what yields; the short lock wait bounds the rest.
- `userPromptSubmit` treats its session upsert and event writes as best effort in one try block (the first locked write ends it) and runs the read-only recall regardless: WAL readers are not blocked by a writer. `recordShown` is written after the recall text is in hand. Recall needs 600 ms of budget left, the adjudicator 1500 ms (`hasBudget`).
- The budget is unset until `dispatch` starts a run (`budgetLeft()` is Infinity), so handlers called directly by tests or tools are never cut short. A late run leaves its budget spent so the abandoned handler skips optional stages.
- Not changed: who holds the long write locks (indexing, usage ingest transactions); `eminiar swarm init --force` still writes through a symlinked .eminiar; the adjudicator already had its own latency budgets (breaker, promptMs 1200, async mode) and was not the cause.

**Why:** the project rule is that hooks fail open within a hard budget; this made the budget real instead of relying on SQLite's default per-statement wait.
**How to apply:** a new hook stage that writes should be best effort or skip under `hasBudget`; do not raise the hooks.json timeout to fix a slow hook, find what it waits on; do not add the 2 s default back for hook connections.
